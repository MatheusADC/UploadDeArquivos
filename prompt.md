1. 🎯 Contexto e Objetivo Principal:Vamos criar um projeto de tela única na qual o usuário poderá fazer o upload de arquivos. Ele terá uma área para para arrastar os arquivos que ele quer fazer o upload e eles arquivos serão adicionados em uma lista logo abaixo, caso eles passem na validação. Após isso ele poderá clicar em um botão de Enviar e será feito o upload de todos esse arquivos de forma paralela, para que seja mais rápido esse processo de upload.

3. 💻 Stack Tecnológica Exata: Esse projeto terá um projeto backend e um projeto frontend, o backend será utilizando o ExpressJS v5 junto com o Typescript v6, já para o frontend será utilizado o Angular v22 junto com Tailwind. Para o gerenciamento dos pacotes será utilizado o NPM, o front e o back terão seus gerenciamentos de pacotes isolados. Para a inicialização dos projetos será o seguinte: o projeto de backend será necessário criar os arquivos de package.json e também o arquivo de configuração do typescript. Para o frontend eu quero que você utilize esse comando "npx @angular/cli@22 new <NOME_PROJETO>", nesse comando será perguntado se o projeto é SSR, eu quero que responda não (N), também será perguntado se será utilizado o Tailwind, eu quero que responda sim (Y), pois dessa forma o próprio script do Angular já configura o Tailwind de forma correta. Para o front não será necessário instalar mais nenhuma lib externa, ex: Angular Material.

4. 📐 Arquitetura e Gerenciamento de Estado: A organização das pastas será o seguinte: na raiz desse diretório será criada uma pasta chamada "backend" e dentro dela será inicializado o projeto backend, além disso também será criado uma pasta chamada "frontend", dentro dela será criado um novo projeto Angular e por fim na raiz do diretório será criada uma pasta para armazenar os arquivos que foram feito os uploads.
Regras do front:
- Para fazer o gerenciamento de estado dos componentes eu quero que seja utilizado o Signals do Angular, para melhorar na performance geral da aplicação.
- Para criar o fluxo de upload eu quero que seja utilizado o RXJS com gerenciamento e tratativas de erro. Pense bem para criar esse fluxo para evitar ter um código imperativo, pois eu quero um código declarativo e reativo seguindo as boas práticas do RXJS e do Signals, dessa forma evitamos de ter muita lógica na parte do subscribe. Caso dê erro no fluxo de upload de algum arquivo, isso não deve barrar o upload do próximo arquivo.
- Para as chamadas das requisições http de upload (provisionamento e upload do binário) eu quero que seja criado um service específico para alocar esses dois métodos e que seja utilizado o HttpClient para realizar as requisições, sem esquecer de tipar corretamente o response de cada uma delas.
- Os componentes devem estar bem organizados também, e não criar todo o código dentro de um único componente, se necessário crie dumb components para ajudar na organização e na fácil manutenção dos componentes.
- Evite criar o template do componente de forma inline, eu quero que o ts esteja separado do html, cada um no seu arquivo.

5. 📏 Padrões de Código e Nomenclatura (Code Style): Tanto para o projeto frontend quanto para o projeto backend eu quero que eles utilizem o padrão de Feature Based Components e MVC (apenas backend), para ajudar na organização dos arquivos e na separação de responsabilidades, ajudando algum desenvolvedor novo entender o projeto sem muitas dificuldades. As interfaces do front e do back eu quero que começem com "I", exemplo: "IUserConfig", e o nome do arquivo dessa interface deve seguir o padrão "user-config.ts", assim fica mais fácil de identificar as interfaces. Esse padrão no nome do arquivo deve ser seguido para os outros, se o arquivo exporta uma classe, o nome dele deve ter o mesmo nome da classe exportada. No front e no back os arquivos devem seguir o padrão kebab-case No projeto Angular eu quero o seguinte:
- Nas versões mais recentes do Angular o suffixo no nome dos arquivos não está mais presente, ex: "wrapper.component.ts" agora seria "wrapper.ts", então eu quero que o nome dos arquivos sejam bem descritivos e que seja intuitivo saber o que esse arquivo faz ao ler o nome dele.
- Quando ocorrer uma injeção de dependência, eu quero que ela siga esse padrão com underline, ex: "private readonly _uploadApi = inject(UploadApi)", dessa forma fica mais simples de identificar as injeções.
- Os métodos privados da classe não precisam ter o underline no nome, apenas as injeções de dependencia públicas ou privadas.

6. 🛑 Regras de Negócio e Validações:
- Provisionamento e Binário: Para fazer o upload completo do arquivos será necessário chamar dois endpoints, o primeiro é o de provisionamento que gera um id para esse arquivo e também outros metadados (data, formato, nome original, extensão, etc), o segundo é o endpint de binário que recebe o binário do arquivo e o id gerado no provisionamento. O backend também precisa fazer as validações de tipo, tamanho e etc no arquivo, para evitar criação de arquivos inválidos.
- Alertas de sucesso, erro e parcial: No frontend eu quero que seja mostrado um Toast indicando o status do upload, podendo ser sucesso (todos os arquivos subiram, toast verde), erro total (todos os arquivos com erro na subida, toast vermelho) e parcial (alguns arquivos com erro e pelo menos um com sucesso, toast laranja). Esse toast deve ser apresentado no canto superior direito da tela e sumir depois de 5 segundos. A implementação do toast deve ser feita de uma forma que eu possa reutilizar ele no futuro em outros componentes, então eu não quero que a implementação dele fique no componente de upload, quero algo reutilizável.
- Iniciar o upload de onde parou, caso tenha dado erro: Caso de erro em algum dos endpoints de upload eu quero que o usuário consiga tentar novamente o upload de onde parou, ex: se o arquivo em específico der erro no provisionamento, será apresentado um botão de Tentar novamente no item desse arquivo e ao clicar nesse botão o upload iniciará a partir do provisionamento, porém se der erro no endpoint de binário, o Tentar novamente deve começar a partir do binário. Isso deve ser feito de forma isolada para cada arquivo.
- Barra de upload incremental para cada arquivo na lista: Cada item da lista que representa o arquivo terá uma barra incremento que acompanha a evolução do upload, se for com sucesso essa barra deve ficar 100% preenchida e com a cor verde, se der erro ela deve ficar 100% preenchida na cor vermelha, durante o incremento ele deverá ter outra cor que você ache adequada. Deve ser utilizado o reportProgress do HttpClient no endpoint de binário.
- Possibilidade de remover um item da lista: Cada item da lista deve ter um botão de X que permite remover esse item da lista.
- Validações dos arquivos: No momento em que o usuário soltar ou selecionar os arquivos, devem ser processadas algumas validações (tamanho, extensão, etc), se o arquivo passar nas validações ele será adicionado na lista, caso contrário ele não é adicionado e será apresentado um toast com o nome original do arquivo ("arquivo.exe") e o motivo dele não ter sido adicionado.
- Limite da lista: No total só podem ter 10 itens na lista de arquivos
- O botão de enviar deve ficar desabilitado caso a lista de arquivos esteja vazia.
- O toast deve ter um comportamento de empilhamento caso mais de um arquivo adicionar seja inválido ou caso múltiplos toasts sejam disparados simultaneamente.
- Após o upload bem-sucedido os itens continuam na lista com a barra em 100% e o botão de remover continua nesse item.

 7. 🛡️ Segurança e Persistência:     
- Fazer um depara e salvar o binário na pasta: Na raiz do desse diretório junto com as pastas "frontend" e "backend" deverá ser criada uma nova pasta para armazenar os arquivos em seus formatos originais. Futuramente se eu implementar uma feature de visualização, eu tenho que conseguir acessar esses arquivos. Além disso deve haver um json na pasta do backend que gerencie os arquivos adicionados, caso futuramente eu queira listar todos os arquivos adicionados e seus detalhes. O backend deve expor essa pasta de uploads como um diretório estático para que o frontend consiga acessar os arquivos futuramente.
- Renomear o nome dos arquivos: Nunca salve arquivos com o nome original, gere um UUIDv4.
- Response dos endpoints: Retorne erros genéricos para o Frontend para não vazar a estrutura do servidor. Esses erros devem ser devidamente tratados no frontend para apresentar uma mensagem para o usuário.
- CORS: Faça uma implementação simples de cors, sabendo que eu vou inicialmente rodar esse projeto no localhost, o front e o back.

8. 🎨 Identidade Visual e UI/UX:
- O código deve estar acessível: Se preocupe em adicionar atributos de acessibilidade.
- Utilizar apenas o tailwind: Não será necessário utilizar outra lib de estilização ou de componentes, apenas o tailwind. Evite criar novas classes nos arquivos do componente, a não ser que seja extremamente necessário. O próprio script de gerar projetos do angular já faz a configuração inicial do tailwind.
- Ícones do windows: Não utilize ícones externos, utilize os ícones do próprio windows para evitar problemas de carregamento, ex: ❌, ✅.
- Fontes: Eu quero que seja utilizado a fonte Roboto do google fonts, para importar ela utilize o formato CDN, não faça nenhuma instalação de lib.
- Mobile First: Utilize o tailwind pensando em mobile first para deixar o código responsivo, o tailwind já é estruturado para mobile first.
- Layout: Eu quero um layout moderno e translucido (Glassmorphism), com fundos escuros, bordas translúcidas, blur.
- Darkmode: Eu quero que você implemente um sistema de darkmode no header da aplicação, então pense bem para organizar a paleta de cores no modo claro e no modo escuro, de forma que fique fácil de gerenciar os temas, e não simplesmente um monte de IFs no template do componente para mudar a cor. Caso o usuário recarregue a tela, o modo que ele escolheu anteriormente deve permanecer. Caso necessário você pode modificar o tailwind.config para criação de temas dark e light, ou utilizar o styles.scss.

9. 🧪 Testes e Qualidade: Para o frontend eu quero que seja utilizado o Vitest padrão da versão 22 do angular, no backend eu quero que seja utilizado o vitest com o supertest. Para os testes de E2E utilize o Playwright

10. 🔮 Features Futuras: Aqui estão algumas features que não serão implementadas agora mas que o sistema deve estar preparado para implementar elas no futuro:
- Listagem e visualização de arquivos adicionados: Será uma listagem que traz os detalhes desse arquivo e ao clicar no item da lista será possível visualizar esse arquivo clicado.
